STAGE 1 - FOUNDATIONS
- fragments/layout.html becomes a small library of parameterised fragments: head(title) (charset, viewport, title, stylesheet, an inline SVG favicon as a data URI so /favicon.ico stops answering 404); nav(active) (the active link gets aria-current="page"; pass the active section as a fragment parameter, do not inspect the request URL inside the template); flash (message and error, with role="status" and role="alert"); pageHeader(title, subtitle); badge(value), which maps an enum value to a CSS class and a human label (PENDING_REVIEW -> Pending review) and is used for every status, severity and priority shown on screen. Every th:replace must pass every parameter its fragment declares (Thymeleaf fails at render time otherwise): when you are done, grep all templates, error.html included, for calls that pass too few.
- Convert all templates to use them: no duplicated <head> or flash blocks any more, <html lang="en">, one <main id="main"> per page, a skip-to-content link.
- Rebuild style.css around design tokens (:root custom properties for colour, spacing scale, radius, shadow, type scale), a centred container (max 1100px), visible :focus-visible rings and prefers-reduced-motion. Keep every existing class name working until no page uses it; define the ones that are used but missing (.button).

STAGE 2 - COMPONENTS
Buttons (.btn with primary, secondary, danger and link variants; a link styled as a button stays a link, a button stays a button), cards, tables (header, row hover, numeric alignment, a wrapper that scrolls horizontally on narrow screens, an empty-state row with a helpful sentence), filter bars as a responsive grid, forms (labels above fields, two columns on wide screens, required markers, helper text, error state: a class on the field plus aria-invalid and aria-describedby pointing at the existing th:errors message, which needs an id added), definition lists as a labelled detail grid, stat tiles on the dashboard with an accent colour and hover and focus states, a progress bar for shelter occupancy only (<progress>, or an element with role="progressbar" and aria values; stock has no honest maximum, so supplies keep their quantity text and the LOW STOCK and OUT OF STOCK badges), flash messages, the error page.

STAGE 3 - PAGE BY PAGE
Dashboard; warnings (list, form, detail); shelters (list, form, detail with the occupancy bar and the occupant table); rescue requests (priority and status badges, assigned team); relief supplies (quantity text, keep the LOW STOCK and OUT OF STOCK badges); relief distributions; ground reports (list; detail with the photo as an image when the Phase 7 <img> exists, an "Open in map" link to openstreetmap.org built from gpsLat and gpsLng, and the review panel with clear primary, secondary and danger buttons); error.html. STAGE 4 - RESPONSIVE, ACCESSIBILITY, CHECKS

- Accessibility: every control has a label, the tab order is logical, focus is always visible, colour is never the only carrier of meaning, text contrast is at least 4.5:1 (compute the ratio of every text/background token pair with a tiny script and show me the table), landmarks (header, nav, main), table header cells with scope.
- Start the app with the local profile and fetch every page with curl.exe: all must answer 200. Grep the returned HTML for leaked template syntax (the patterns th:[a-z]+=, \$\{ and ~\{; a bare "th:" or "__" gives false hits), for "Whitelabel" and for "Exception". Stop the app afterwards and make sure no java process you started is left running.
